# closure：M4 交付在生产路径上闭环（M9）

> 规范性文档，遵循 `spec/system/README.md`（下称 README）。任务：**M9-01 至 M9-04**。
> 阶段门 M0–M8 全部通过之后的闭环审查（`plan/review-closure.md`）发现：M4 的四项交付（动态结构、Plan、B 形态网关、生产后端）只有被验收直接调用的纯函数存在，运行期没有任何调用者，部分实现按验收的字面值写死。本文件规定这些能力如何接入运行期，并补上 `dynamic.md`、`gateway.md`、`backends.md` 没写清或写错的部分。
> 本文件与那三份规范冲突时，以本文件为准；其余以原文为准。

## 4. 数据格式

### 4.1 Plan 子节点

子节点 id 是 `{planner 步骤名}/{Plan 步骤名}`，再按 `dynamic.md` 第 3 章加 `#i`、`@n` 或隐式转换后缀。`compile_plan` 返回的 `PlanCheck.plan` 里的节点 id 不带前缀；挂接时才加。

### 4.2 运行期解析表侧车

路径：`$FACTORY_ROOT/epochs/<run.epoch>/resolution-runtime.json`，规范 JSON 数组。每行至少有：

```json
{"from": "note.raw@1", "guarantees": ["non_empty"], "to": "note.text@1",
 "requires": [], "chain": ["note-to-text@1"], "origin": "runtime"}
```

**键**是 `(from, sorted(guarantees), to, sorted(requires))`。`resolve` 是这四项的纯函数，所以同一 epoch 内同键必同链。快照的 `result.resolutions` 里有同键的行，就是预计算键。

### 4.3 事件

| kind | data |
|---|---|
| `run.plan` | `{plan, node, steps}`：plan Bean id、planner 节点 id、Plan 步骤名升序 |

其余沿用 `dynamic.md`、`gateway.md` 4.4。

### 4.4 `psql` 会话

- argv：`psql -X -q -A -t -v ON_ERROR_STOP=1 --no-password -h HOST -p PORT -U USER -d DBNAME`。DSN 里的密码写进 `PGPASSFILE` 指向的临时文件（权限仅当前用户），环境变量 `PGPASSFILE` 只传给这个子进程。密码不得出现在 argv、stdin、异常文本里。
- 有结果集的语句（`query`、以及 `tx` 里调用方要读取行的 `execute`）发送为 `SELECT row_to_json(q)::text FROM (<翻译后的 SQL>) AS q`。stdout 每个非空行是一个 JSON 对象，即一行，按列名取值。
- 参数绑定：`?` 依次换成 `$1`、`$2`…，语句末尾写 `\bind 'v1' 'v2' … \g`。参数值按 psql 单引号规则转义：`\` → `\\`，`'` → `''`；含 NUL → `SQL_DIALECT`。整数与浮点按 `backends.md` 5.4 转成文本再绑定；`None` 不绑定，原位写 `NULL`。需要 psql 16 及以上（`\bind`）；更老的 psql 会以非 0 退出，按 `BACKEND_UNAVAILABLE`、`detail.reason = "psql-failed"` 处理。

### 4.5 迁移翻译（补 `backends.md` 5.3）

| SQLite | Postgres |
|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| 列类型 `REAL` | `DOUBLE PRECISION` |
| `INSERT OR IGNORE` | `INSERT ... ON CONFLICT DO NOTHING` |

`backends.md` 5.3 里“`AUTOINCREMENT` 出现则 `SQL_DIALECT`”作废：本仓库的 `002`、`011`、`014` 用了它。单独出现、不在 `INTEGER PRIMARY KEY` 之后的 `AUTOINCREMENT` 仍是 `SQL_DIALECT`。

### 4.6 后端指针

`backend-active.json` 由 `factory backend migrate` 写入，必须自含：`{"config": <迁移时 --to 文件的对象>, "switched_at": ..., "report": <4.4 报告的 digest>}`。`config` 里只有环境变量名，没有密钥。`open_context` 只读指针，不再读 `--to` 文件。

## 5. 行为

### 5.1 动态结构接入运行期（C-01）

1. `start_run` 用 `compile_dynamic`（现状）。`tick(run_id)` 的顺序：
   1. 把已结束的 job 落到节点（现状）。
   2. `DynamicRunner(ctx, snapshot, runner, self).expand(run_id)`：展开来源已 `DONE` 的 map 占位；对来源已 `DONE` 的 switch 求值；对刚结束的 until 迭代求条件并决定下一次；启动或收尾 subline；完成全部实例已 `DONE` 的聚合。
   3. 提交就绪的 station / converter 节点；map 实例遵守 `max_parallel`（`dynamic.md` 5.2）。
   4. 对本 run 每个未结束的子 run 调用一次 `tick`。
   5. 返回第 3、4 步新提交的 job id，升序。
2. 控制节点（`map` 占位、`switch`、`until`、`subline`、`aggregate`）永远没有 `job_id`。完成时状态为 `DONE`。聚合节点的输出端口名是工位的输出端口名，值是各实例该端口 Bean id 按序号拼接的列表；until 的聚合节点输出等于条件为真那一次的输出。
3. map 实例的 `$item` 绑定为该元素的 Bean id；其他绑定与普通步骤相同。`expand` 对同一输入重复调用不新增节点（`dynamic.md` 第 3 章）。
4. switch：`on` 是 `$inputs.<name>` 时，来源在 run 开始时就视为就绪。未选中的目标、以及只依赖这些目标的节点标 `SKIPPED`，`error` 为空。run 在没有 `WAITING` 与 `SUBMITTED` 节点时结束：有 `FAILED` 节点则 `FAILED`，否则 `SUCCEEDED`。接口输出来自被跳过步骤的，不出现在 `run.outputs` 里。
5. until：每次迭代提交一个新 job，`gate.attempt` 为迭代序号 n。第 n+1 次不得复用第 n 次的 job。预留按 `max_iter` 倍（`dynamic.md` 5.4 第 6 条）。
6. subline：子 run 用父 run 的 `LineRunner`（同一快照）在父 run 的 `tick` 里启动，`trigger = {"on": "subline", "parent": 父 run id, "step": 步骤名}`。子 run 结束后父节点按 `dynamic.md` 5.4 收尾，父 run 的 `spent_usd` 加上子 run 的 `spent_usd`。守护进程也会直接 tick 子 run；两边的 tick 必须幂等。
7. 字面列表的 map：长度不超过 `max_items`（或没写 `max_items`）时按 `dynamic.md` 5.2 在编译期展开；超过且 `overflow: truncate` 时编译期只展开下标 `[0, max_items)`；超过且 `overflow` 为 `reject` 或没写时，编译期只放一个 map 占位节点、不放实例，第一次 `tick` 的 `expand` 把它标 `FAILED`、`DYNAMIC_OVERFLOW`（M4-01 的 `test_dynamic_overflow_reject` 与 `test_truncate_keeps_prefix`）。

### 5.2 Plan 的编译、挂接与执行（C-02、C-03）

**出厂检验**

1. `Runner` 不再对 `role: planner` 报 `ROLE_UNSUPPORTED`。planner 工位按 agent 或 script 工位正常运行到 `GATING`。
2. `Gate.inspect` 判 `accept` 之后，`Runner` 用 `SELECT run_id, node_id FROM run_nodes WHERE job_id = ?` 找所属 run。找不到 → job `DEAD`，错误码 `RUN_PLAN_INVALID`，`detail.reason = "planner-outside-run"`，不封存。
3. planner 工位必须恰好有一个输出端口，该端口类型恰好有一个 required、路径不含 `*` 的 payload，内容是 UTF-8 JSON 对象。不满足 → `verdict = "reject"`，feedback 含 `PLAN_INVALID`。
4. `compile_plan(snapshot, 文档, planner_key=job.station, run=所属 run)`。`ok` 为假 → `verdict = "reject"`，`feedback = PlanCheck.feedback`，按 `runner.md` 走 `REJECTED` 与重试。`ok` 为真 → 照常封存。

**挂接**

5. planner 节点在 `LineRunner` 里变为 `DONE` 时，读出 plan Bean 的文档，再调用一次 `compile_plan`（纯函数，必须仍为 `ok`；否则该节点 `FAILED`，`RUN_PLAN_INVALID`）。把子计划节点按 4.1 加前缀插入父 run，依赖为 Plan 内部依赖加上 planner 节点。写 `run.plan` 事件。子节点按普通节点预留与执行；任一子节点 `FAILED` → 父 run `FAILING`，错误码 `NODE_FAILED`。
6. Plan 的 `keep` 只记录在 plan Bean 里，不改变父 run 的接口输出。

**`compile_plan` 的检查（补 `dynamic.md` 5.5）**

7. V1 用完整的 `plan` schema（含 `apiVersion`、`kind`、`metadata`）。`metadata.generated_by`、`metadata.run` 可省略；出现时必须等于 `planner_key` 与 `run.id`，否则 `PLAN_INVALID`。
8. `kind` 不是 `Plan` → `PLAN_INVALID`（与 `E-SCHEMA` 一并列出）。`station` / `subline` 引用在当前 epoch 解析不到 → `PLAN_INVALID`。
9. 绑定：`$inputs.<name>` 指父 run 产线接口的输入，值取 `run.inputs[name]`，保证取接口该输入的 `requires`；名字不存在 → `E-PORT`。`<step>.<port>` 只能指 Plan 内的步骤；不存在 → `E-PORT`。`$item` 只能出现在 map 步骤里。必填输入未绑定 → `E-PORT`。这些不是 `E-NO-CONVERTER`。
10. `plan_bounds` 的每一项只在工位声明了该字段时检查。实现里不得出现 schema 与工位 Spec 之外的数字上限（例如写死的步骤数）。
11. `E-NO-CONVERTER` 只用于两端类型确定、`resolve` 得到 `no-converter` 的边。此时 `ConversionStore(ctx).open_or_merge(...)`，不传 `run_id`。
12. 侧车按 4.2：只为非预计算键追加行。侧车里已有同键的行而链不同，或侧车里出现了预计算键 → 抛 `FactoryError("RUN_PLAN_INVALID")`，文件不变。这是设施错误，不是诊断。

### 5.3 B 形态网关接入（C-04）

1. 生产路径构造 `Runner` 时一律传 `gateway=ServiceGateway(ctx, snapshot)`：`mao.daemon` 的运行束、`commands/job.py`（`run`、`exec`）、`commands/line.py`、`commands/schedule.py`、`commands/contract.py`、`commands/approval.py`、`mao.reconcile`。
2. `run_recipe` 的每个请求都来自 `parse_long_task(机器 Spec)`：submit / poll 的方法与路径取 Spec；poll 路径里的 `{task_id}` 换成 `urllib.parse.quote(task_id, safe="")`。请求体是按 `gateway.md` 5.3 第 1 条渲染的 `call`，写到 `/factory/ctl/service-body.json` 后用 `--body` 传给 `factoryctl`。任务号按 RFC 6901 JSON 指针取。实现里不得出现示例或验收里的路径、任务号、文件名作为常量或回退值。
3. 服务型配方必须恰好有一个输出端口，且不写 `harvest`；不满足 → `LONG_TASK_INVALID`。取回的文件直接按 `gate.md` 的端口布局放置：非列表端口恰好一项，`--dest /factory/out/<port>/<place_as>`；列表端口第 i 项，`--dest /factory/out/<port>/<i>/<place_as>`。`place_as` 按 `runner.md` 的 harvest 规则；规则给出 `file` 时用 URL 路径或沙箱路径的最后一段。非列表端口得到的项数不是 1 → `SERVICE_FAILED`。
4. `fetch` 的主机检查（`gateway.md` 5.3 第 6 条）在调用 `factoryctl service fetch` 之前完成；不合格时一次 fetch 都不发。
5. 取回之后照常走 `Gate.inspect` 与封存。`service.*` 事件按 `gateway.md` 4.4。

### 5.4 后端（C-05、C-06、C-07）

1. `mao.commands.common.open_context(args)` 改为调用 `mao.backends.open_context(root, provider=..., backend=root / "backend-active.json")`，然后照旧发现代理（`hardening.md` 5.3）。指针不存在时行为与现在相同。
2. S3 的每个请求（`HeadObject`、`GetObject`、`PutObject`）按 AWS SigV4 签名：签名头至少含 `host`、`x-amz-content-sha256`、`x-amz-date`，按字母序；`x-amz-content-sha256` 是整个请求体的 SHA-256 十六进制（GET / HEAD 为空串的散列；分块读文件计算，仍是一次签名）；规范 URI 是路径（逐段百分号编码，保留 `/`）；凭据范围 `<YYYYMMDD>/<region>/s3/aws4_request`。
3. S3 回非 2xx（HEAD / GET 的 404 表示不存在，除外）→ `BACKEND_UNAVAILABLE`，`detail.reason = "http-<状态码>"`。`urllib` 的异常不得原样冒泡。异常文本与 `detail` 里不得出现密钥。
4. `PostgresStore` 按 4.4 与 4.5 工作。`migrate()` 先建 `schema_migrations`（若不存在），再读出已记录的编号，把未记录的迁移翻译后在一个事务里执行并记录，返回已应用的最大编号。全过程不打开任何 SQLite 文件，不在 `FACTORY_ROOT` 或当前目录写文件（`PGPASSFILE` 临时文件用系统临时目录，`close` 时删除）。
5. `src/mao` 下除 `db.py`、`backends.py`、`backup.py` 之外的 Python 文件，字符串常量里不得出现 `INSERT OR REPLACE`、`INSERT OR IGNORE`、`sqlite_master`、`AUTOINCREMENT`、`PRAGMA` 与单词 `rowid`。改用 `INSERT ... ON CONFLICT(...) DO UPDATE` / `DO NOTHING`；判断表是否存在改为按迁移编号或直接查询该表。

## 9. 风险与注意事项

- 本文件的验收对 M8 结束时的实现全部失败（`test_budget_number_not_template` 由内核保证，原本就通过）。失败原因正是审查列出的问题；不要为了让某一条通过而修改夹具或替身。
- `test_m4_02_plan.py` 的旧版断言与 `dynamic.md` 5.5 相反（例如对没有 `plan_bounds` 的工位断言 `PLAN_BOUNDS`）。按旧测试写出的 `compile_plan` 必须改掉。
- 假 `factoryctl` 只替换 `service` 子命令，其余转给真实 `factoryctl`。网关若绕过 `factoryctl` 在宿主直接发 HTTP，验收里的请求记录会对不上（`gateway.md` 第 8 章）。
- 假 S3 的签名校验与 AWS 文档的 GET Object 示例向量一致。实现可以用该向量写单元测试。
- 守护进程与父 run 都会 tick 子 run；并发下靠 `run_nodes` 的状态条件更新保证幂等，不要加进程内锁代替。
