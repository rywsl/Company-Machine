# M15-03 运行确认

- 状态：未开始。依赖 M15-02 完成后才能 `task start`。
- 规范：`spec/system/talk.md`（第 3.2、4.4、5.6 节）、`spec/system/commands.md` 的 M15 增补、`plan/design-talk.md`。
- 允许修改：见 `plan/tasks.yaml` 中本任务的 `paths`。
- 验收测试：`tests/acceptance/m15/test_m15_03_confirm.py`（6 个）。夹具 `tests/acceptance/m15/talk_world.py`。

## 要做什么

- 厂长 MCP 工具 `talk_propose_run` 只追加 `proposed` 卡片，并开收件箱通知，不调用 `start_run`。
- `factory talk answer ID --by NAME --confirm` 调用 `answer(..., confirm=True)`。它用 `EpochRouter.choose` 选 epoch，再调用 `LineRunner.start_run`。`trigger` 恰好是 `{"on": "talk", "by": <人>, "message": <卡片 id>}`。
- `answer` 成功时返回新追加的状态消息，`card.status` 为 `PENDING`。原卡片仍是 `proposed`。线程字段 `by` 仍是 `control`，确认的人在 `card.by`。
- 没有 `--confirm` 得到 `TALK_CONFIRM_REQUIRED`，不启动 run。确认普通消息、重复确认，分别是 `TALK_NOT_CONFIRMABLE`、`TALK_ALREADY_ANSWERED`。
- run 后来的状态经 `note_status` 写回线程。

## 不要做

- 不要让厂长绕过确认直接 `start_run`。`run_start` 仍只属于 agent 角色。
- 不要在确认时调用 `advance`、`merge`、`rollback` 或 `run_to_completion`。
- 不要加拒绝动词。不确认的卡片保持 `proposed`。
- 不要加控制台路由。
- 不要在实现里使用夹具的产线名或 Bean 文本作为分支条件。
- 不要修改受保护的规范、验收测试与夹具；不要新增第三方依赖；不要调用模型 API；不要 `shell=True`。
- 验收与规范矛盾时写 `plan/journal/` 并 `task block`，不要猜。
