# M17 常驻执行、消息与自主周期：基线诊断

- 基线：`c538768a586637870cad47bfc48e5d5da6163150`；M15 实现和 M16 已冻结的设计，未包含正在进行的 M16 实现。
- 环境：Linux WSL2 x86_64，Python 3.14.2，uv 0.9.4；离线依赖。测试为隔离本地工厂、假时钟和本地 CLI 替身，没有付费 API、外部消息或真实生产系统。
- 诊断文件：`plan/evidence/m17/repro/test_host.py`。它不是 M17 完成验收；在本基线中，失败断言是对预期正确行为的反例。正向对照确认同一测试夹具可以完成正常 CLI 工作轮。
- 可重跑：先 `mkdir -p .factory/m17-repro`，然后运行：

```bash
uv run --offline python tools/harness.py pytest plan/evidence/m17/repro/test_host.py -q --tb=short --basetemp .factory/m17-repro/host-audit
```

  `host-audit` 是此测试独占的临时目录；pytest 在重跑时会重建该目录。一次完整结果：`total=9, passed=1, failed=8, errors=0, skipped=0, exit=1`。`test_local_agent_diagnostic_fixture_can_complete_mail` 通过；8 条失败分别对应 H01–H08。逐项运行时将 `plan/evidence/m17/repro/test_host.py` 换成 `plan/evidence/m17/repro/test_host.py::test_函数名`。

## H01 普通 CLI 的 serve 不启动常驻 Agent

- 分类：已复现的旧规范接线错误。`spec/system/agents.md` 5.7 要求 `factory.json` 有 `agents` 时使用 `daemon.epochs` 启动 `AgentHost`。
- 复现：`test_cli_serve_starts_configured_resident_host` 真正启动 `python -m mao ... serve` 子进程，预先写入 helper 邮件并等待；模型调用以有效 stream-json 的本地 CLI 替代。
- 实际：进程存活、持有 `serve` 租约，`agents` 租约不存在，消息仍为 `pending`。
- 根因：`src/mao/commands/serve.py:63` 未传 epoch，`src/mao/daemon.py:687-695` 虽有 `daemon.epochs` 却只检查参数 `epochs`。`tests/acceptance/m13/test_m13_03_turns.py:181` 手动传参，因此没覆盖 CLI。
- 统一修复约束：从实际 CLI 装配后的资源启动 AgentHost；验证失败须有明确健康状态。回归应同时证明现有单快照/无 agents 组合的边界，不得用直接调用替代 CLI。

## H02 启动异常使已投递消息永远卡住

- 分类：已复现的恢复漏洞；旧规范缺少领取后启动异常的完整结案语义。`agents.md` 5.3 描述失败后消息重试，5.5 只要求启动时恢复 running 轮次。
- 复现：`test_cli_launch_error_does_not_strand_delivered_mail` 使用真实 LocalProvider，将 Agent 可执行文件映射到不存在路径；失败后恢复正常 CLI，再尝试下一轮。
- 实际：`message_state='delivered'`、轮次 `running`、`retry_executed=False`；无需中止整个 serve 也会持续卡住。
- 根因：`src/mao/agents.py:628-697` 在 CLI 准备前提交 `running/delivered`，`serve` 只捕获并记录 tick 异常（496–514），`recover` 只在启动时执行（436–467）。
- 统一修复约束：领取到执行结束的所有故障点必须有可恢复结案；区分从未启动与执行结果不明，避免重复外部副作用。回归覆盖构建调用、沙箱创建、CLI 启动、日志归档等阶段失败和重启。

## H03 唤醒票领取和邮箱写入之间丢失，恢复后仍 taken

- 分类：已复现的跨事务恢复缺口。旧 `agents.md` 5.8 依赖邮箱负责常驻厂长唤醒票，但未明确中间崩溃的原子性。
- 复现：`test_taken_wake_survives_mailbox_write_failure` 对真实 `WakeQueue` 和 `AgentHost.collect`，在 `Mailbox.post` 前注入一次写失败；执行 `recover` 再 `collect`。
- 实际：`wake_state='taken'`、`matching_mail=0`，后续再取票也无法获得。
- 根因：`src/mao/agents.py:882-900` 的领取和写邮箱分属独立事务，恢复仅检查 `agent_turns`。受影响的审批、转换、故障票可能永久无人处理。
- 统一修复约束：领取与投递要原子化或有可靠的可对账恢复；每票只对应一次可重试投递。回归包含进程在两步之间终止以及重复恢复。

## H04 定时消息提交后中断会重复投递

- 分类：已复现的重放/幂等语义缺口；旧 `agents.md` 5.2 没有将投递与水位更新定义为单一事务。
- 复现：`test_schedule_post_is_not_duplicated_across_interruption` 在首次 `Mailbox.post` 已提交后、更新 `agent_schedule.last_at` 前注入异常，恢复后再次 collect。
- 实际：同一时间点的同一 `schedule:0` 产生 `am-0001`、`am-0002` 两条消息。
- 根因：`src/mao/agents.py:532-560` 先独立提交消息，后提交调度水位。Bean 订阅 `src/mao/agents.py:562-603` 也有“先批量投递、后推进游标”的相似窗口；后者只是代码推断，尚未在本报告单独复现。
- 统一修复约束：同一订阅/计划的同一次触发，投递与水位应一致或有稳定事件键去重；不同时间点不得被错误去重。测试需包含单次中断、多次恢复和下一次正常计划。

## H05 agents 租约失效后旧宿主继续工作

- 分类：已复现的旧规范违例。`spec/system/durable.md` 3.1 明确 `LeaseKeeper.lost` 后持有方必须停止该资源工作。
- 复现：`test_lost_agents_lease_stops_host` 用真实租约存储和加速的真实 `LeaseKeeper`，删除 `agents` 租约模拟失去所有权，等待续约失败。
- 实际：日志出现“租约已丢失 resource=agents”，但 `host_alive_after_lease_removed=True`。
- 根因：`src/mao/agents.py:496-514` 从未检查 `keeper.lost`。若新宿主随后接管，两个宿主都可能派发；本测试证明旧宿主未停止，未直接声称已观测到两次真实外部提交。
- 统一修复约束：获取和续约丢失后停止新轮次，并定义在途执行的 fencing、停止与结果不明处理；不能仅在循环尾部检查而让失权宿主继续提交外部效果。

## H06 空 CLI 输出被当成工作成功

- 分类：已复现的旧契约弱点，不应误称单纯实现违例。`operator.md:263` 明确空 stream-json 的 `is_error=false`，`agents.md:412-413` 又允许没有摘要时按退出码 0 完成；`agents.md:529` 的“不会静默丢上下文”风险说明与这种组合不一致。
- 复现：`test_empty_successful_cli_output_is_not_completed_work` 用真实 `/usr/bin/true` 作为 CLI，退出 0 且不产生 transcript。
- 实际：`turn_state='ok'`、`session=None`、`message_state='done'`。
- 根因：`src/mao/operator.py:149-192` 对空文件返回 `is_error=false`，`src/mao/agents.py:699-729,1541-1556` 接受退出码 0 并结案。
- 统一修复约束：先决定常驻 agent 的成功证据、初次会话 ID/恢复确认和无效输出处置；兼容一般 script/历史 runtime 的既有含义。无证据不能静默丢消息、累计为成功或假装能续接。

## H07 并发领取唤醒票时两个消费者获得同一张票

- 分类：已复现的旧规范违例。`spec/system/foreman.md:261` 要求两个进程同时取票时只有一个成功。
- 复现：`test_wake_claim_is_exclusive_under_concurrency` 用屏障令两个真实调用同时完成 open 查询，再竞争条件更新。
- 实际：`claims=['wk-0001','wk-0001']`，两个调用都返回同一张票。
- 根因：`src/mao/foreman.py:80-98` 在事务外先查询，事务内 `UPDATE ... AND status='open'` 不检查影响行数，竞争失败者仍读取并返回他人取得的票。
- 统一修复约束：竞争失败者必须重新寻找可领取票或返回无票；结合 H05 的失权隔离和 H03 的投递恢复做并发/重启验证。

## H08 随机消息 ID 使实际派发顺序与“按时间”相反

- 分类：已复现的规范冲突。`agents.md` 4.5 承诺给 Agent 的消息“按时间排列”，5.3 却规定按 `id` 排序。生产 `RandomIds` 是随机字符串（`src/mao/base.py:148-152`），并非递增编号；`CounterIds` 测试则掩盖问题。
- 复现：`test_batch_order_matches_chronological_prompt` 先后入队“开始”和“取消”，使用两个合法但字典序倒置的消息 ID，假时钟推进 1 秒。
- 实际：创建顺序 `['am-zzzzzzzzzz','am-aaaaaaaaaa']`，投递顺序相反。`src/mao/agents.py:1350-1356` 的 `_pending` 按 id 排序。
- 统一修复约束：设计应先裁决真实顺序语义，包括同一时间戳并发、延迟消息和重试；仅改显示文本无法修复后果。建议固定持久单调入队序号，避免依赖 wall clock 或随机 ID 推测因果顺序。

## H09 一次宏观目标后没有下一周期

- 分类：现有 M13/M15 的能力边界，已在新增持续自治需求下复现；不是 M16 正在实现的 `agent_send`/`remind` 接线缺陷。
- 复现：本地成功 CLI 首轮处理一次 `foreman` 消息；之后不增加外部人或 Agent 消息、不产生新唤醒票，假时钟每次前进 1 小时并 collect/run_once，连续三次。
- 实际：首轮 `ok`、`foreman_schedule=[]`；第 1、2、3 小时的 `next_turn` 都为 `None`、邮箱 pending 均为 0。`src/mao/agents.py:204-247` 内置厂长的 schedule 和 Bean 订阅为空，`src/mao/agents.py:416-434` 无消息即不执行。
- 本验证仅证明缺少默认持续驱动；不代表厂长无法处理由其他机制显式投入的事件，也不代表任意业务任务永远都应该自动运行。
- 统一设计约束：M17 应明确宏观目标授权、持久目标与周期状态、有限观察/规划/执行/评估的调度触发、成本与暂停条件、故障后从上次可证明阶段续接。验收需由人只提交一次目标，在无新的外部触发/指令的条件下至少完成多个可追踪周期；暂停/预算耗尽须有清晰终态。M16 的知识和交接接口按其完成后可用的规范集成，不重造或改写其正在进行的实现。

以下命令重跑上述观察；目录是独立测试工厂，结束后临时目录由 Python 清理：

```bash
mkdir -p .factory/m17-repro
uv run --offline python - <<'PY'
import json, sys, tempfile
from pathlib import Path
from tests.acceptance.m13.agent_world import World
from tests.fakes.fakelib import FAKE_AGENT_COMMAND
with tempfile.TemporaryDirectory(prefix="host-idle-", dir=".factory/m17-repro") as tmp:
    w = World(Path(tmp).resolve(), foreman={"mode": "resident"})
    code = 'import json; print(json.dumps({"type":"result","subtype":"success","is_error":False,"session_id":"stable-session"}))'
    w.ctx.provider.commands[FAKE_AGENT_COMMAND] = [sys.executable, "-c", code]
    host = w.host()
    w.post("foreman", "长期宏观目标：持续寻找并完成有价值的工作")
    first = host.run_once("foreman")
    later = []
    for hour in range(1, 4):
        w.clock.advance(3600)
        host.collect()
        turn = host.run_once("foreman")
        later.append({"hour": hour, "next_turn": None if turn is None else turn.id,
                      "foreman_pending": len(w.messages("foreman", state="pending"))})
    print(json.dumps({"first_turn": first.state,
                      "foreman_schedule": host._config_for(w.snapshot, "foreman").schedule,
                      "later": later}, ensure_ascii=False))
    w.ctx.close()
PY
```

## 边界和后续验收

以上结果证明的是固定基线上的局部路径，不能替代真实模型、Docker 隔离、M16 完成后集成或真实支付/外部副作用的端到端验收。诊断没有修改 `src/`，也没有将任何缺陷标成已修复。H03/H04/H05/H07 的共同修复边界是可恢复的领取、投递、去重和失权停止；H01/H02/H06/H08 共同涉及 CLI 运行协议、轮次与消息的可靠状态；H09 属于更上层的目标驱动闭环，不能靠延长超时或额外塞一条人工消息解决。
