# M7-03 受阻：相同内容无法形成两个共享 blob 的 Bean

- 时间：2026-11-11
- 任务：M7-03 保留期、墓碑与回收
- 现象：`uv run python tools/harness.py pytest tests/acceptance/m7/test_m7_03_retention.py` 中 `test_shared_blob_survives` 失败。其余 7 个通过。关键输出：两次 `Warehouse.add` 相同 `note.text@1` 与相同字节得到同一个 id `sha256:697d2e37bffc6db0a63f081b2fabc9e8b85296be68cb5cdb0ff8d84543f52408`；第一次回收把这唯一的引用标成墓碑后 `blobs_deleted == 1`，测试要求 `0`，并在再过 10 天后把另一个 id 过期。
- 规范依据：`spec/system/warehouse.md` 第 3 章，原文：“id = digest_bytes(canonical_bytes(身份对象))”。身份对象是 type、meta、payload。`spec/system/retention.md` 5.2 要求死 digest 的判定是“引用它的每一行都属于已过期 Bean”。验收 `test_shared_blob_survives` 用同一类型、同一字节调用两次 `_bean`，却断言两个 id、先过期的那个不删 blob。
- 我的理解：A. 遵守仓库身份，相同内容就是同一个 Bean，这条验收无法通过。B. 让 `add` 对相同内容再发一个新 id，共享 blob 测试能过，但会打破 `warehouse.md` 和 M1 已经锁定的内容寻址。
- 已经尝试：按 5.1–5.4 实现了过期、钉住、隔离、在用、共享 digest 判定、dry-run 和目录回收。前 7 个测试通过。单独确认两次 `add` 的 id 相等。
- 建议：人改 `tests/acceptance/m7/test_m7_03_retention.py` 的 `test_shared_blob_survives`，用不同 meta 或不同路径造两个 Bean、同一 payload digest；或者在规范里写明同一内容可以有多个 Bean。在此之前不要改 Bean id 公式。
- 后续：评估要求把第二次 `add` 改成不同 meta。PreToolUse hook 拒绝编辑 `tests/acceptance/m7/test_m7_03_retention.py`。按 `plan/README.md` 第 6 节，不绕过 hook。受阻继续有效。
