# Основные понятия

У Machine Agent Org небольшая метамодель. Всё, что можно построить (видеоконвейер, линию код-ревью, ночной отчёт), выражается семью примитивами, перечисленными ниже. Они записываются как YAML-**Spec** в Git-реестре. Компилятор структуры проверяет эти Spec так же, как проверка типов проверяет код.

> Обоснование архитектуры: разделы 3–10 [`docs/architecture.md`](../architecture.md) (на китайском). Формальные правила: [`spec/mrl/factory-profile.md`](../../spec/mrl/factory-profile.md).

## 1. Примитивы

| Примитив | Значение | Ключевые моменты |
|---|---|---|
| **Type** (тип) | спецификация материала | `name@major.minor`. Виды: атомарный, `bundle{…}`, `list<T>`, `ref<T>`, `any`. Содержит схему размещения полезной нагрузки, схему метаданных, валидаторы (с фикстурами на приём и отказ), измеряемые *факты* и именованные *свойства* |
| **Bean** (единица материала) | одна порция материала | адресация по содержимому (`sha256:…`), неизменяемость, запечатывается вместе с историей и источником происхождения |
| **Machine** (машина) | существующий продукт | описывается Machine Package: образ, закреплённый по digest, рецепты, входы и выходы, пробы, эталоны соответствия |
| **Operator** (оператор) | тот, кто управляет машиной | CLI агента (Claude Code в headless-режиме, Codex), скрипт или человек через входящие |
| **Station** (станция) | Recipe × Operator × Policy | типизированные порты. Роли: `source`, `transform`, `sink`; `converter`, `judge` и `planner` — специализированные преобразования |
| **Line** (линия) | типизированный DAG из станций | плюс ограниченные динамические конструкции. Линию с интерфейсом можно использовать как станцию (`subline`) |
| **Policy** (политика) | права | уровень выхода в сеть, секреты, бюджет, согласования, публикация, сроки хранения |

Над ними стоят три понятия метауровня. **Spec** — любое из перечисленных выше определений; оно хранится как Bean типа `spec.<kind>@N`. **Invariant** (инвариант) — правило конституции, записанное на MRL. **ChangeSet** — diff между Spec, и сам он тоже Bean. Поскольку собственная структура фабрики — это тоже материал, те же проверки могут защищать и работы по обслуживанию. Именно так держат в рамках бригадира (Foreman).

## 2. Типы, факты и свойства

Тип объявляет *факты*, которые измеряют валидаторы, и *свойства* — именованные выражения MRL над этими фактами.

```yaml
# spec/examples/registry/types/video.yaml (фрагмент)
kind: Type
metadata: {name: video.mp4, version: "1.3"}
spec:
  extends: video@1
  payload:
    - {path: video.mp4, media_type: video/mp4, required: true}
  validators:
    - name: ffprobe-facts
      run: [probe-video, /bean/payload/video.mp4]
      emits: [duration_s, width, height, fps, vcodec, audio_streams, mean_volume_db]
      fixtures:
        accept: [fixtures/video/ok-1920x1080.mp4]
        reject: [fixtures/video/truncated.mp4, fixtures/video/png-renamed.mp4]
  properties:
    has_audio: "bean.facts.audio_streams > 0"
    vertical:  "bean.facts.height > bean.facts.width"
    hd:        "(bean.facts.width < bean.facts.height ? bean.facts.width : bean.facts.height) >= 1080"
```

Каждый валидатор поставляется с фикстурами на приём и на отказ. Изменение, из-за которого фикстура на отказ начинает проходить, то есть пропускать плохой материал, автоматически относится к высокому уровню риска.

## 3. Контракты потребителей: `guarantees` и `requires`

Порты формулируют контракты в терминах свойств. Выходной порт перечисляет, что он **гарантирует** (`guarantees`), и выходной контроль (gate) это обеспечивает. Входной порт перечисляет, что он **требует** (`requires`).

```yaml
# spec/examples/registry/stations/vertical.yaml
kind: Station
metadata: {name: vertical, version: 1}
spec:
  role: transform
  machine: ffmpeg@3
  recipe: reframe-vertical
  operator: {runtime: script@1}
  inputs:  {video: {type: video.mp4@1, requires: [hd, has_audio]}}
  outputs: {video: {type: video.mp4@1, guarantees: [vertical, hd, h264, has_audio, not_silent]}}
  limits:  {timeout: 15m, budget_usd: 0}
  policy: tool-default@1
```

На этапе компиляции каждое ребро должно удовлетворять условию `requires ⊆ guarantees ∪ type properties`. Это включение множеств, поэтому, когда вышестоящая станция отказывается от какой-либо гарантии, компилятор точно называет, какие нижестоящие порты ломаются. Во время выполнения проверка на входе вычисляет те же свойства на реальном Bean.

## 4. Конвертация: продукты автоматически становятся материалом

Если типы или свойства на ребре не совпадают, компилятор ищет в реестре станции-**конвертеры** (`converter`) и вставляет ровно одну цепочку. Если подходят несколько цепочек, он выбирает по правилам в таком порядке: сначала без потерь, затем с наименьшим числом шагов, затем с наименьшей оценочной стоимостью, затем с наименьшим оценочным временем, затем по имени. Вы видели это в разделе [Начало работы](getting-started.md): переход `note.raw@1 → note.text@1` обеспечил `note-to-text@1`. Если цепочки нет, компилятор не гадает. Он сообщает `E-NO-CONVERTER`, а *запрос на конвертацию* будит бригадира, который может предложить новый конвертер.

## 5. Линии

```yaml
# spec/examples/registry/lines/explainer-multilang.yaml (фрагмент)
kind: Line
metadata: {name: explainer-multilang, version: 5}
spec:
  interface:
    inputs: {brief: {type: brief.video@1}}
  trigger:
    - {on: bean, type: brief.video@1, label: "line=explainer-multilang"}
  budget: {cap_usd: 12.0}
  steps:
    explainer: {station: explainer@3, in: {brief: $inputs.brief}}
    dub_en:    {station: dub@2, params: {target_language: en},
                in: {video: explainer.video, subtitle: explainer.subtitle}}
    vertical:  {station: vertical@1, in: {video: dub_en.video}}
    to_s3:     {station: publish-s3@2, params: {bucket: media-archive, prefix: "explainers/{{ run.id }}/"},
                in: {artifact: vertical.video}}
```

Правила:
- Каждый конечный продукт должен потребляться каким-либо sink (станцией публикации) или быть указан в `keep`.
- Бюджеты иерархичны: глобальный → линия → запуск → станция → задание.
- Триггерами могут быть поступление `bean`, расписания `cron` или `every` либо ручной запуск.

### Ограниченная динамическая структура

| Конструкция | Что делает | Ограничение |
|---|---|---|
| `map` | выполняет подшаг для каждого элемента `list<T>` | `max_items` (при переполнении — отказ или усечение), `max_parallel` |
| `switch` | выбирает одну ветвь по условию MRL | должен быть исчерпывающим, с `default` |
| `until` | повторяет подшаг, пока не выполнится условие MRL | `max_iter`; при исчерпании запуск завершается сбоем |
| `subline` | выполняет другую линию внутри эпохи текущего запуска | ограничение глубины |
| `plan` | станция-**планировщик** (planner) выдаёт `Plan` (под-DAG) | компилируется проверками V1/V2 и сверяется с `plan_bounds` до того, как что-либо будет выполнено |

## 6. Эпохи: изменения без поломки текущей работы

Каждый коммит реестра, прошедший проверку, может стать **эпохой** (epoch — зафиксированной версией структуры). Запуск привязывается к одной эпохе при старте и сохраняет её до завершения, поэтому изменение структуры никогда не влияет на уже идущую работу. Откат означает перенос указателя текущей эпохи назад. Одновременно в работе могут находиться несколько эпох, например активная эпоха и канареечная рядом с ней.

## 7. Шесть уровней проверки

| Уровень | Что проверяется | Когда | При неудаче |
|---|---|---|---|
| **V1** Spec | схема, ссылки, закреплённые версии, линт политик | при каждом предложении | изменение отклоняется |
| **V2** Структура | типы и контракты рёбер, циклы, обязательные входы, потребление выходов, права, бюджет, динамические ограничения | предложение + перед каждым запуском | отклоняется изменение / запуск |
| **V3** Эволюция | совместимость с предыдущей версией, все контракты нижестоящих потребителей, радиус поражения | предложение | отказ или требование конвертера миграции |
| **V4** Контрактные тесты | соответствие машин, эталонные brief, конвертация туда и обратно, пробные прогоны sink | предложение + плановые канареечные запуски | отказ или оповещение о дрейфе |
| **V5** Среда выполнения | проверка на входе, выходной контроль (структура → валидатор → приёмка → судья), проверка квитанций sink | каждое задание | отказ → повтор, или DLQ |
| **V6** Непрерывная | аудит инвариантов, мониторинг дрейфа, целостность CAS и истории происхождения, согласование состояния | периодически + по событиям | карантин, размыкание цепи, откат, пробуждение бригадира |

## 8. Четыре вида дрейфа

| Дрейф | Пример | Чем обнаруживается |
|---|---|---|
| Дрейф спецификаций | кто-то редактирует тип или порт | V1–V3 и контракты потребителей |
| Дрейф поведения | продукт обновился, сменились модель или промпт | закреплённые версии, канарейки V4, теневые запуски |
| Семантический дрейф | вывод по-прежнему соответствует схеме, но качество падает | выражения приёмки, выборочные судьи, базовые значения метрик |
| Дрейф конфигурации | контейнеры или привязки секретов изменены в обход процесса | согласователь состояния и аудит инвариантов |

## 9. Уровни управления

Конвейер проверки детерминированно выводит уровень риска из diff каждого ChangeSet. Понизить его не может никто, включая бригадира.

| Уровень | Типичное изменение | Требования |
|---|---|---|
| T0 | повтор, карантин | автоматически |
| T1 | настройка шаблона, новый конвертер, минорное повышение версии типа | проверка + теневой запуск |
| T2 | подключение или обновление машины, новая линия, мажорное повышение версии типа | + канарейка + перекрёстное ревью другой средой выполнения |
| T3 | новый source/sink, выход в сеть или привязка учётных данных, изменение политики, вывод из эксплуатации | + согласование человеком |
| T4 | конституция | только люди |

Конституция (L0) — последний якорь. Машины и агенты могут перестроить всё остальное, но только через проверенные, доступные для ревью и обратимые ChangeSet.
