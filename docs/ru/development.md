# Разработка

Machine Agent Org разрабатывается с явным разделением ролей на **проектировщика и исполнителя**. Его обеспечивает детерминированный harness `tools/harness.py`, так что ни одна из сторон не может незаметно сдвинуть планку.

## 1. Роли

| Роль | Отвечает за | Не может |
|---|---|---|
| **Проектировщик** | спецификации (`spec/`), план и карточки задач (`plan/`), приёмочные тесты (`tests/acceptance/`), ревью | писать промышленный код |
| **Исполнитель** | `src/`, системные тесты (`tests/system/`), записи в журнале | менять спецификации, приёмочные тесты или критерии приёмки; придумывать интерфейсы; забегать вперёд текущей вехи |
| **Человек** | конституцию, ADR и **перерегистрацию защищённых файлов** (`harness lock --update`) | — |

Защищённые файлы перечислены glob-шаблонами в `plan/protected.lock` и закреплены по SHA-256. Хук PreToolUse (`.claude/settings.json`) отклоняет попытки агентов их редактировать, а `harness lock --verify` обнаруживает любое изменение. Если исполнитель находит противоречие, он останавливается, делает запись в `plan/journal/` и выполняет `harness task block`. Проектировщик исправляет защищённый файл, а человек перерегистрирует блокировку.

## 2. Рабочий цикл harness

```bash
uv run python tools/harness.py doctor            # окружение
uv run python tools/harness.py status            # вехи, задачи, контрольные точки
uv run python tools/harness.py task next         # первая задача, все зависимости которой выполнены
uv run python tools/harness.py task show M9-01   # карточка задачи и обязательные материалы к прочтению
uv run python tools/harness.py task start M9-01
# … реализация …
uv run python tools/harness.py accept M9-01      # запускает приёмочные проверки задачи, записывает доказательства
uv run python tools/harness.py gate M9           # контрольная точка этапа: все проверки вехи (и унаследованные)
```

Другие подкоманды:
- `doccheck`: таблицы тестов в главе 7 спецификаций должны совпадать с тестовыми функциями.
- `check`: одна проверка по имени.
- `scenario`: сценарии из `plan/scenarios/`.
- `pytest`: запускает pytest и выводит сводку в JSON. Всегда используйте его вместо обычного `pytest`: он настраивает путь импорта для пакета `tests`.
- `lock --verify`: сравнивает защищённые файлы с блокировкой.

Доказательства (команды, коды выхода, дайджесты вывода, коммит git) записываются в `plan/state.json`.

## 3. Вехи

```mermaid
flowchart LR
    M0["M0<br/>компилятор структуры"] --> M1["M1<br/>одна станция"] --> M2["M2<br/>линии и внешний мир"] --> M3["M3<br/>управление и бригадир"] --> M4["M4<br/>динамика и продакшен"]
    M4 --> M5["M5<br/>контур автономности"] --> M6["M6<br/>настоящие CLI агентов"] --> M7["M7<br/>эксплуатация"] --> M8["M8<br/>исправления по ревью"] --> M9["M9<br/>завершающие исправления"]
```

Каждая веха заканчивается в рабочем состоянии, готовом к передаче, и каждая контрольная точка этапа наследует проверки предыдущей. M5, M8 и M9 — *корректирующие* вехи. Каждая из них появилась после ревью проектировщика, обнаружившего возможности, которые проходили свои тесты, но не были подключены к промышленному пути (`plan/drift.md`, `plan/review-m5-m7.md`, `plan/review-closure.md`). Урок, ставший теперь правилом для приёмочных тестов: **работать через промышленные точки входа, а фейки должны проверять поведение.** Фейковый S3 пересчитывает SigV4, фейковый `psql` протоколирует каждый вызов, а фейковый `factoryctl` передаёт настоящие метод и путь.

## 4. Тесты

| Уровень | Где | Что |
|---|---|---|
| Приёмочные | `tests/acceptance/m0…m9/` | по одному файлу на задачу, названному в главе 7 спецификации; защищены |
| Системные | `tests/system/` | модульные и интеграционные тесты, за которые отвечает исполнитель |
| Соответствия | `spec/mrl/conformance/`, `tests/test_conformance.py` | сценарии MRL для выражений, правил и фабрики; существующие сценарии можно только дополнять |
| Политики | `tests/test_codebase_policy.py`, `tests/test_hooks.py` | статические правила для `src/mao` (никаких импортов через monkey-patching, никакого доступа к текущему каталогу, никакого обращения к приватным частям других модулей, …) |

Тестовые дублёры лежат в `tests/fakes/`:
- `fake_agent.py` — сценарный двойник Claude Code. Его поведение задаётся файлом `task.json` в Bean с задачей.
- `fake_llm.py` — upstream модели для уровня live.
- `tools/` содержит инструменты для фикстур.

Реестры фикстур — `tests/fixtures/registry-m1` и `registry-m2`. Уровням с Docker нужен `uv run python tools/build_test_images.py`. Без Docker они пропускаются; задайте `MAO_REQUIRE_DOCKER=1`, чтобы вместо этого они завершались неудачей. Контрольные точки этапов требуют ноль пропусков.

## 5. Правила кода

Они взяты из `spec/system/README.md` (решения D1–D14) и `plan/README.md` § 6:

- Python ≥ 3.12. Зависимости времени выполнения — только стандартная библиотека, `pyyaml`, `jsonschema` и `mrl` из самого репозитория. Новая зависимость требует ADR. CLI Docker вызывается как подпроцесс, SQLite — через `sqlite3`.
- Никаких `shell=True`. Никаких вызовов API LLM: интеллект поступает только из CLI операторов.
- **MRL — единственный язык выражений и шаблонов.** Шаблоны в Spec компилируются через `mrl.expr`; `eval`, Jinja и `str.format` для содержимого Spec запрещены.
- Библиотечный код получает пути из `Context.root` или от вызывающей стороны, но никогда из текущего каталога.
- SQL времени выполнения должен быть переносимым между SQLite и PostgreSQL. Специфичные для SQLite конструкции допускаются только в `db.py`, `backends.py` и `backup.py`.
- `uv run ruff check src tests tools` и `uv run ruff format --check` должны проходить; длина строки — 110.
